## 0. Контекст

Часть системы уже реализована и работает в проде. Это ТЗ фиксирует, что меняется поверх существующей системы по итогам разбора хендоффа и интервью с заказчиком.

## 1. Итог: что меняется

| Область | Сейчас | Должно быть |
|---|---|---|
| План | Один общий план на компанию в месяц | Общий план компании + отдельный план на каждого подрядчика |
| «Зоны внимания» | Захардкоженный порог CPL > 1500 ₽, считается по MTD | Отклонение >20% от **личного** плана подрядчика по любой из 5 базовых метрик, за выбранный период (неделя/месяц) |
| «Нет данных» | Только отсутствие лидов | Нет лидов ИЛИ не введён расход за прошлую неделю |
| Ввод расхода | Ручное поле в паспорте подрядчика (вкладка «Расход», таблица `weekly_facts`) | Отдельный раздел «Ввод расходов», не в паспорте; авторасчёт по 2 из 3 моделей оплаты |
| История | Таблицы `weekly_snapshots`/`monthly_snapshots` созданы, не заполняются | Ручная заморозка периода админом — навсегда фиксирует цифры и план на момент заморозки |
| Дата/неделя | Баг: местная полночь конвертируется в UTC, дата уезжает на день назад | Единая функция расчёта «сегодня» в явной таймзоне Europe/Moscow |
| Bitrix-импорт | Работает, поля и логика дат подобраны эмпирически | Без изменений, кроме фикса даты (раздел 2) |

## 2. Критичный баг: расчёт «сегодня»

> **Обнаружено при подготовке этого ТЗ.** Импорт данных за сегодня в проде временно недоступен через интерфейс — выпадающий список дней его не показывает, пока баг не исправлен. Исправить в первую очередь, до остальной части ТЗ.

Три места в коде вычисляют «сегодня» и границы отчётной недели одинаково неверно:

- `src/pages/ImportPage.jsx` → `computeDateContext()`
- `src/pages/DashboardPage.jsx` → `getWeekStart()`
- `src/lib/helpers.js` → `weekStart()`

Паттерн ошибки — локальные методы (`setHours`, `setDate`) выставляют локальную полночь, а форматирование идёт через `.toISOString()`, которая всегда переводит время в UTC:

```js
today.setHours(0, 0, 0, 0)          // локальная полночь, напр. 00:00 по Новосибирску (UTC+7)
today.toISOString().split('T')[0]   // = "вчера 17:00 UTC" → отдаёт вчерашнюю дату
```

Для любого часового пояса восточнее UTC (Новосибирск UTC+7, Москва UTC+3 — то есть всей России) это даёт систематический сдвиг на день назад в `computeDateContext()`, а в двух других местах — сдвиг в ранние утренние часы, пока UTC не «догонит» локальный день. Это прямой кандидат на причину открытого в хендоффе вопроса о расхождении лидов/квалов 5–10% между приложением и Bitrix.

**Требование к исправлению:**

- Один общий модуль (например `src/lib/dateContext.js`), который вычисляет «сегодня» и границы отчётной недели явно в таймзоне `Europe/Moscow` — через `Intl.DateTimeFormat('en-CA', { timeZone: 'Europe/Moscow', year:'numeric', month:'2-digit', day:'2-digit' })` (даёт готовую строку `YYYY-MM-DD`), а не через `toISOString()` на локальном `Date`.
- Тот же модуль используют `ImportPage.jsx`, `DashboardPage.jsx`, `helpers.js` — никаких параллельных реализаций.
- Edge Function `bitrix-import` проверяется отдельно на тот же паттерн ошибки (она на Deno, может считать дату иначе — нужна ревизия).
- Значение «сегодня» пересчитывается не только при монтировании компонента, а также при возврате фокуса на вкладку (`visibilitychange`) — чтобы не залипало на вчерашнем дне при долго открытой вкладке.

## 3. Отчётная неделя

Неделя ЮК «Опора» — **четверг → среда**. Это правило не меняется, оно уже верно закодировано (баг из раздела 2 — про часовой пояс, не про день недели).

**Редактируемое окно (обновлено с учётом заморозки):**

- Текущая (незакрытая) неделя — редактируется всегда.
- Только по четвергам — доступна ещё и только что закрывшаяся предыдущая неделя, для финальной сверки.
- **Новое:** как только предыдущая неделя заморожена админом (раздел 9), она выпадает из редактируемого окна полностью — независимо от дня недели. Правило проверяется и на фронте, и на сервере (Edge Function), как и раньше.

## 4. Метрики

Источник — рабочий макет дашборда, подтверждённый заказчиком. Пять базовых метрик — единственные, которые участвуют в планировании и «Зонах внимания» (раздел 5). Остальные шесть — производные, показываются только для информации.

**Базовые (входят в план):**

| Метрика | Что считает | Направление «плохо» |
|---|---|---|
| Расход | Сумма расхода за период (см. раздел 8) | факт **выше** плана |
| Лиды | Кол-во лидов, дата создания (`DATE_CREATE`) | факт **ниже** плана |
| Квалы | Кол-во квалифицированных лидов, дата квалификации | факт **ниже** плана |
| Встречи | Кол-во проведённых встреч, дата встречи | факт **ниже** плана |
| Сделки | Кол-во сделок, дата входа в стадию оплаты | факт **ниже** плана |

**Производные (только для справки):**

| Метрика | Формула |
|---|---|
| CPL | Расход / Лиды |
| CPQL | Расход / Квалы |
| CAC | Расход / Сделки |
| CR(l→q) | Квалы / Лиды |
| CR(q→m) | Встречи / Квалы |
| CR(m→o) | Сделки / Встречи |

## 5. Планирование — два уровня

### 5.1 План компании

Существующий механизм (`monthly_targets`, модалка «Задать план») сохраняется как источник плана для агрегированных карточек дашборда. Вводится один раз в начале месяца.

> **Предлагаемое упрощение.** Сейчас форма плана компании просит вручную вводить все 11 значений, включая производные (целевой CPL, целевой CPQL, целевой CAC, все три CR). Раз производные метрики нигде не участвуют в контроле отклонений — предлагаем оставить в форме только 5 базовых полей (Расход, Лиды, Квалы, Встречи, Сделки), а плановые значения CPL/CPQL/CAC/CR на карточках дашборда считать автоматически из них (`план_CPL = план_Расход / план_Лиды` и т.д.). Это уберёт из формы 6 полей, которые сейчас можно сделать несогласованными с базовыми вручную.

### 5.2 План подрядчика — новая сущность

В отличие от плана компании, план подрядчика — **не месячный**. Он вводится один раз при заведении подрядчика в базу (часть формы создания подрядчика) и дальше живёт как есть, пока кто-то вручную его не скорректирует — никакого обязательного ежемесячного переввода.

Новая таблица, например `contractor_targets`: `contractor_id` (уникальный), `plan_spend`, `plan_leads`, `plan_quals`, `plan_meetings`, `plan_deals`, `updated_at`, `updated_by`. Только 5 базовых метрик — без производных, без измерения «месяц» в ключе.

- Обязательное поле при создании подрядчика (`AddContractorModal.jsx`) — без плана нового активного подрядчика завести нельзя.
- Редактируется вручную в любой момент (например, из вкладки «Обзор» паспорта) тем же ответственным, что ведёт план компании.
- Вводится **для всех статусов с `is_active = true`** (В переговорах, Новый, Тест, Активен, Под контролем, Снижен объём — раздел 10.1), без исключений.
- В режиме «Неделя» на дашборде и в «Зонах внимания» план подрядчика делится на неделю тем же коэффициентом, что уже используется для компании (`1 / 4.33`).

## 6. Дашборд

Общая раскладка (переключатель Месяц/Неделя, селектор периода, 6 карточек KPI, таблица доп. показателей) — как в согласованном макете, без изменений в вёрстке. Меняется источник данных и логика двух правых колонок.

### 6.1 Источник данных по периоду

- Текущий (незамороженный) период — считается «вживую» из `weekly_stats` / `daily_facts` + `weekly_expenses`, как сейчас.
- Замороженный период — читается из `weekly_snapshots` / `monthly_snapshots`, не пересчитывается заново. Подробности заморозки — раздел 9.

### 6.2 «Зоны внимания» — логика переписывается

**Как сейчас:** захардкоженный порог (`cpl_mtd > 1500` или «расход есть, лидов нет»), считается по MTD, без связи с личным планом подрядчика.

**Как должно быть:** для каждого подрядчика не в исключённом статусе (раздел 10.1) — сравнить факт с его личным планом (раздел 5.2, приведённым к выбранному периоду) по каждой из 5 базовых метрик. Если хотя бы одна метрика отклонилась в «плохую» сторону (раздел 4) более чем на **20%** — карточка подрядчика попадает в «Зоны внимания», с перечислением *всех* нарушенных метрик и величины отклонения по каждой (не только первой найденной).

> **Пример.** Подрядчик «Маркетикс», план на неделю: 20 лидов, факт 14 (−30%, порог 20% — нарушен) и план по расходу 15 000 ₽, факт 15 200 ₽ (+1.3% — в норме). В карточке «Зон внимания» показываем только «Лиды: −30% (14 из 20)».

### 6.3 «Нет данных за период»

**Как сейчас:** только отсутствие лидов за период.

**Как должно быть:** подрядчик попадает в этот список, если за выбранный период **нет лидов** ИЛИ **не введён расход** за только что закрывшуюся неделю (см. раздел 8). Это два разных по смыслу сигнала (первое — проблема с самим подрядчиком, второе — забыли внести расход), но в макете они показываются одним списком; при желании можно разделить подписью на карточке, какая именно причина сработала.

`ContractorsPage.jsx` — раскладка не меняется. Меняется только источник алерта: счётчик «Превышение CPL» и подсветка в колонке CPL сейчас держатся на том же захардкоженном пороге 1500 ₽. ## 8. Модели оплаты и ввод расхода

### 8.1 Модели оплаты — только три

В БД сейчас 6 типов в справочнике `payment_types` (CPL, Фикс, Абонентка, Абонентка + бюджет, Процент, Смешанная). В работу берём только три — остальные скрыть из выпадающих списков в UI (не удалять из таблицы, чтобы не сломать исторические данные, если такие уже есть).

| Модель | Ввод | Формула |
|---|---|---|
| Фикс | Автоматически, ввод не нужен | `cpl_rate × лиды за неделю` (по дате создания, без вычета брака) |
| Абонентка | Полностью автоматически, поле ввода не показываем вообще | `retainer_месяц / 30.41 × 7` |
| Абонентка + бюджет | Часть авто, часть вручную | `ad_budget_недели (вручную) + retainer_месяц / 30.41 × 7 (авто)` |

> **Изменение схемы.** Сейчас `sources.ad_budget` — статичное поле на источнике (заполняется один раз). Для модели «Абонентка + бюджет» это должно стать еженедельным ручным вводом в `weekly_expenses`, а не постоянным значением на источнике. `sources.retainer` и `sources.cpl_rate` остаются статичными (месячная абонентка и ставка за лид не меняются каждую неделю).

### 8.2 Раздел «Ввод расходов» — новый, отдельно от паспорта

- Отдельный пункт в сайдбаре (не вкладка внутри паспорта подрядчика) — вкладку «Расход» в паспорте удалить вместе со старым ручным вводом в `weekly_facts`, чтобы не оставалось двух источников правды.
- Открывается по четвергам, выбор — только что закрывшаяся неделя (по умолчанию), с возможностью посмотреть предыдущие уже введённые недели.
- Список подрядчиков не в исключённых статусах (раздел 10.1). У каждого — одно поле расхода, если `spend_by_source = false`, либо по одному полю на каждый активный источник, если `spend_by_source = true`.
- Поле для источника с моделью «Фикс» или «Абонентка» — **только отображение** посчитанной суммы, недоступно для редактирования.
- Поле для «Абонентка + бюджет» — ручной ввод суммы бюджета за неделю; итоговая сумма (бюджет + доля абонентки) показывается рядом как посчитанная.
- Сохранение — в `weekly_expenses`: `source_id`, `week_start`, `manual_amount`, `auto_amount`, `total_amount`, `is_auto_calculated`, `entered_by`, `entered_at`.

## 9. Заморозка периодов

Таблицы `weekly_snapshots` / `monthly_snapshots` уже созданы, логика заполнения — нет. Замораживание — ручное действие, не по расписанию: ответственный сверяет цифры с Bitrix в четверг и после этого сам нажимает «Заморозить неделю».

**Правила:**

- После заморозки данные периода **навсегда неизменны** для всех, кроме отдельно оговорённого администратора.
- В снапшот копируются не только факты (лиды/квалы/встречи/сделки/расход по каждому подрядчику), но и **плановые значения, действовавшие на момент заморозки** — иначе последующее редактирование плана задним числом незаметно исказит историческую картину отклонений. Это была исходная причина отказа от VIEW «на лету» ещё в прошлой сессии — сохраняем этот принцип и для планов, не только для фактов.
- Разморозка / пересчёт — доступны только администратору, с явным подтверждающим диалогом («это перезапишет зафиксированную историю»).
- После заморозки период выпадает из редактируемого окна импорта (раздел 3).

> **Решено: без технического ограничения доступа.** Системы авторизации в приложении нет и на этом этапе не заводим. Заморозка/разморозка остаются доступны любому, кто открыл раздел — полагаемся на то, что кнопку видит и использует только один человек (заказчик). Если позже появится второй администратор или подрядчики получат доступ к своему кабинету, к этому вопросу нужно будет вернуться (минимальный логин через Supabase Auth или PIN на кнопку).
